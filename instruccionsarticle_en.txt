Practical Evaluation: Preparation of a scientific article based on the Distributed Applications project
Completion Requirements
Opening: Friday, July 31, 2026, 11:00
Closing: Friday, July 31, 2026, 13:00

Each student must prepare a scientific article based on the project developed during the Distributed Applications course. The manuscript will be prepared using the Springer template provided by the professor.

The article should not be limited to presenting the software, describing its screens, or listing its functionalities. The developed application will be used as a proof of concept, experimental prototype, or case study to investigate a problem related to distributed architecture, security, inter-service communication, scalability, performance, storage, artificial intelligence, or other content applied during the semester.

The main component of the article will be the investigated idea, the applied method, the evaluation performed, and the knowledge obtained. The software will constitute the means to verify this idea and obtain evidence, but it will not represent the scientific contribution on its own.

Although the projects may correspond to different domains, each student must identify a technical aspect that can be analyzed, compared, or evaluated. The results should allow formulating conclusions, criteria, or recommendations that can be considered in other systems with similar characteristics.

Objective
Prepare a scientific article presenting the architecture, methodology, evaluation, and knowledge contribution obtained through the development and analysis of a distributed application.

Selection of the Research Topic
The topic must be logically selected and maintain a direct relationship with the functionalities implemented in the project. A technology or comparison should not be chosen solely because it is available or was studied during the course.

Before defining the article, the student must analyze:
    What technical problem is presented in their project.
    Which component can be evaluated through testing.
    Which scenarios can be compared.
    What metrics can be obtained.
    What knowledge can be derived from the results.
    To what extent the findings could be useful for other applications.

For example, a sales system could analyze transactional consistency, payments, or asynchronous processing; a document application could study file protection; a system with artificial intelligence could compare local models and external services; while a clustered application could evaluate replicas, availability, or request distribution.

Definition of the Knowledge Contribution
The student must select a technical problem related to their project. They can work with one of the following approaches:
    Comparison between synchronous and asynchronous communication.
    Evaluation of direct processing versus the use of message queues.
    Performance analysis with one replica and multiple replicas.
    Evaluation of Docker Swarm or Kubernetes for request distribution.
    Comparison of authentication mechanisms such as JWT, OAuth 2.0, and TOTP.
    Evaluation of sending emails synchronously and via an asynchronous worker.
    Analysis of public storage versus protected file storage.
    Evaluation of temporary or signed links to protect resources.
    Comparison between a local artificial intelligence model and one consumed via API.
    Measurement of response time of a functionality with and without artificial intelligence.
    Behavioral analysis of a payment gateway for approved, rejected, or canceled transactions.
    Evaluation of error handling, logs, and failure recovery.
    Analysis of the impact of pagination on queries with different amounts of records.
    Evaluation of logical deletion and information recovery strategies.
    Comparison of system behavior under different levels of concurrency.
    Evaluation of service availability given the interruption of a replica.

Another approach may also be proposed, provided it generates measurable results, maintains a relationship with the implemented architecture, and allows obtaining a broader contribution than the product description.

Research Question
The article must answer a specific, delimited, and testable question. For example:
    How does the use of a message queue influence the response time for sending emails?
    What effect does the number of backend replicas have on handling concurrent requests?
    What are the differences between consuming a local artificial intelligence model and using an external API?
    How does file protection improve using temporary links compared to access via public links?
    What behavior does a distributed application exhibit in the event of external payment service failures?
    How does pagination affect query time when the number of records increases?
    What effect does the interruption of a replica have on service availability?
    How does resource usage vary when processing notifications synchronously and asynchronously?

The question must relate to a functionality implemented and verified within the project. When appropriate, a hypothesis can also be proposed to be subsequently tested through the results.

Methodology
The student must perform controlled tests on their application. At a minimum, they must:
    Define the component or process to be evaluated.
    Establish at least two comparable scenarios.
    Identify variables that will be modified and those that will remain controlled.
    Define the metrics used.
    Execute multiple tests under the same conditions.
    Record the complete results.
    Present the data using tables or graphs.
    Analyze the differences found.
    Identify potential threats to validity.
    Formulate conclusions based on the evidence.

The metrics may include:
    Response time.
    Number of requests handled.
    Percentage of successful or failed requests.
    Memory or processor usage.
    Processing time.
    Number of messages processed.
    Service availability.
    Error recovery time.
    Quality or relevance of an AI-generated response.
    Number of authorized and rejected accesses.
    Transactional consistency.
    Error rate.
    Throughput per unit of time.
    Behavior under different concurrency levels.

The tests must be reproducible. The tools used, versions of technologies, environment characteristics, service configuration, number of executions, and conditions applied in each scenario must be specified.

Article Structure

Title
The title must describe the problem studied, the approach applied, or the evaluated technology. Using solely the project's commercial name should be avoided.
Example:
Evaluation of an asynchronous architecture for sending notifications in a distributed application

Abstract
The abstract will be between 150 and 250 words and must present the problem, objective, methodology, main results, contribution, and conclusion. At the end, between four and six keywords will be included.
The abstract must contain concrete results. General expressions such as "good results were obtained" will not be used without presenting the data supporting this claim.

Introduction
The introduction must explain:
    The context of the problem.
    Its technical or practical importance.
    The limitations identified in existing solutions.
    The research question.
    The objective of the study.
    The main contribution of the article.
    The organization of the manuscript.
The last section of the introduction must explicitly state the contribution of the work.

Related Work
Research related to the studied problem will be presented. This section should compare approaches, architectures, technologies, metrics, and results reported by other authors.
It should not become a collection of definitions. Each source must relate to the developed work and allow identifying a difference, limitation, or aspect that will be addressed in the article.
At least ten sources will be used, prioritizing scientific publications from the last six years, counted from the year the manuscript is prepared. Scientific articles must have a valid and verifiable DOI. Official documentation, standards, or technical resources lacking a DOI must include their bibliographic information and corresponding link.
All cited sources must appear in the references section, and every included reference must be mentioned within the text.

Solution Architecture
The architecture used as the experimental environment will be explained, including:
    Main components.
    Frontend and backend.
    Services.
    Database.
    Replicas.
    Message queue.
    Communication mechanisms.
    Authentication and security.
    External services.
    Deployment.
A general architecture diagram must be included. The explanation should focus on the components related to the investigated problem and avoid an extensive description of modules not involved in the tests.

Methodology
The following will be described:
    Study design.
    Evaluated scenarios.
    Independent and dependent variables.
    Metrics.
    Tools.
    Environment configuration.
    Data used.
    Execution procedure.
    Number of repetitions.
    Method used to organize and analyze the results.
The methodology must allow another person to repeat the tests under equivalent conditions.

Results
Only data obtained through real tests executed on the project will be presented.
The results must include:
    Comparative tables.
    Graphs.
    Values obtained.
    Observed behavior.
    Recorded errors or failures.
    Evidence necessary to verify execution.
Screenshots may be used as backup but will not replace tables, metrics, or quantitative analyses.

Discussion
The discussion must interpret the results and explain:
    What the obtained data mean.
    Why the differences occurred.
    How they relate to the research question.
    In what aspects they agree or differ from other works.
    What advantages and limitations the proposal presents.
    In what contexts the results could be applied.
    What threats affect the validity or generalization of the study.
The values shown in the results section will not merely be repeated.

Conclusions and Future Work
The conclusions must directly answer the research question and present the knowledge obtained through the tests.
The following must be indicated:
    The main finding.
    The contribution of the study.
    The conditions under which the result was obtained.
    The limitations.
    Derived recommendations.
    Possible lines of future work.
The conclusions must not incorporate results that have not been presented previously.

References
References must be prepared using the style defined by the Springer template.
Scientific articles must include author, title, publication, volume, issue, pages, year, and a valid DOI. Sources must be verified before incorporating them into the manuscript.

Format and Length
The article will have a length of between 12 and 15 pages, including figures, tables, and references.
The provided Springer template will be used. The document can be prepared in:
    Microsoft Word using the official template.
    LaTeX using the Springer template for Computer Science proceedings.
When LaTeX is used, the main .tex file, figures, the .bib or .bbl bibliographic file, the files required for compilation, and the generated PDF must be delivered.
Margins, fonts, font size, spacing, or template structure must not be modified in order to artificially reduce or increase the length.

Authorship
The student must appear as the first author of the article and the professor as the second author.
The following must be correctly registered:
    Full names.
    Institutional affiliation.
    Institutional email.
    ORCID, when available.
        Example https://orcid.org/0000-0002-7715-7706, otherwise https://orcid.org/0000-000a-bcde-fghi.
    Identification of the corresponding author, when required.
The order of authorship must be maintained in the editable document and the PDF file.

Quality of Figures, Tables, and Diagrams
All figures must be presented in suitable quality for publication. Architecture, flow, and process diagrams should preferably be generated in vector format, such as SVG, PDF, or EPS.
Screenshots or rasterized images must:
    Maintain their original resolution.
    Be legible at the size presented in the article.
    Avoid excessive deformations, cropping, or scaling.
    Avoid compression via messaging applications.
    Show only necessary information.
    Hide passwords, tokens, secrets, and personal data.
Line drawings and diagrams must use a minimum resolution of 800 dpi, preferably 1200 dpi. The internal text of the figures must retain a legible size.
Figures must be numbered and have the title at the bottom. Tables must be numbered and have the title at the top. All must be mentioned and analyzed within the text.
Tables must remain editable and must not be inserted as screenshots.

Important Considerations
The article must focus on the knowledge obtained through the project. Screens, forms, modules, or code snippets will only be used when necessary to understand the architecture, methodology, or experimentation.
The software must function as a proof of concept or case study for the investigated proposal. The contribution must lie in the approach, comparison, evaluation, method, architecture, or evidence obtained, and not merely in having built an application.
The selection of the contribution must be consistent with the project. Comparisons or technologies will not be incorporated without a technical reason, a specific question, and metrics that allow evaluating them.
It will not be valid to claim that a technology is better, faster, secure, efficient, or scalable without presenting tests, metrics, or sources supporting the claim. Each result must be analyzed considering the conditions under which it was obtained.
Data may not be invented, altered, or selected solely to favor a conclusion. Negative results, errors, and limitations must also be reported when they are part of the experimentation.
The manuscript must include the link to the project's public repository. The repository must contain:
    Updated code.
    README.md file with clear installation and execution instructions.
    .env.example file with the structure of the environment variables.
    LICENSE file.
    Configurations necessary to run the project.
    Scripts, data, or files used to reproduce the tests.
    Exclusion of passwords, tokens, private keys, and secrets.
When the tests use personal data or sensitive information, the student must anonymize it and explain the measures applied to protect it.

Deliverable
The student must submit:
    Complete article in PDF format.
    Editable document prepared with the Springer template.
    LaTeX source files, when this format is used.
    Link to the updated public repository in an activity comment.
    Evidence of execution of the evaluated scenarios.
